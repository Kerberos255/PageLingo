## 缓存实际行为

键包含正式模型SHA、原HTML、源/目标语言、上下文和完整术语项。排队前复制请求及术语，避免等待时被调用方修改。只缓存已通过现有解码/完整性检查的结果；拒绝、异常和取消结果不缓存。关闭、移除（经close）及开始下载清空；清空后的旧在途任务不能重新填入缓存。相同并发请求在串行队列中只产生一次成功推理，已命中的请求可直接返回。

复用既有LRU实现，最多256项、输入8192 UTF-16 code units，缓存键值字符串合计不超过2,097,152 code units；这不包含JS对象开销，不声称是整个进程的内存上限。不持久化网页内容。缓存对象向调用方分别返回，不共用可变结果对象。

## 质量实验及没有采用的协议

生产提示用不透明P占位隐藏代码实际值，可能让模型看不到动作参与者。先登记一个候选：在P后内联原值JSON字符串，语法强制其原位置和字面值，完整检查后压回原P，再使用现有固定文字槽解码器。没有第二份完整上下文、目标草稿或参考译文；所有文字槽位置和max_tokens保持。超长原值/上下文直接拒绝，不裁剪原值。

独立新样本为MDN ReadableStream.getReader、PostgreSQL约束、Node.js错误处理各两段，按先登记的关系词优先、DOM顺序规则选择。本地61个文件、1291个归一化源哈希中无重叠；不能证明基模预训练或不可见主力机旧语料未包含网页。六段各做生产/候选/自然文本18次，加14个既有诊断案例的候选14次，**实验新增32次：31 EOS、1长度截断**。旧14条生产基线只有请求消息/grammar/预算与模型哈希完全相同才复用，不算新生成；没有重抽失败样本或在结果后调整提示。

| 固定协议解码/结构回放 | 独立6段 | 既有14段 |
|---|---:|---:|
| 生产协议 | 5显示 / 1截断拒绝 | 13显示 / 1括号拒绝 |
| 内联原值候选 | 6显示 | 13显示 / 1括号拒绝 |

显示数不能当作语义正确数。逐原句评阅发现：

- getReader生产输出把“释放这个读取器”改成“释放此流”，动作参与者错误；候选恢复读取器，却多出不必要的尖括号。
- 新getReader异常段在两种固定协议中，underlying source从句均有缺失/病句；候选还把带反斜线的type=bytes复制到代码之外。自然译文从句较好，但将受保护ReadableStream类名译成中文，不能直接回填。
- Node的must强调段，生产协议把后文挤进错误槽后循环输出全角END直到预算耗尽，整段保留原文；候选正确保留must原强调及进程退出条件，是局部改善。
- 两个PostgreSQL约束段两方案显示文字完全相同。
- 旧createImageBitmap候选却变成“Window接口的Promise方法……返回一个ImageBitmap”，把Promise绑定到方法而非返回值，漏掉resolves，并重复Window含义。截图可见语义错误，即便所有链接代码仍在原节点。
- 旧Rust的while x valid条件仍弱化成“而x有效”；Fetch的promise仍译作“承诺”，但本轮保留了404例外否定。No ARIA候选仍有多余闭括号，被原有保护拒绝。

因此 **不启用候选**。原值可见性是部分原因，固定位置下的参与者/条件/谓语分配仍不稳；这也不足以判定基础 `tencent/Hy-MT2-1.8B` 必须更换。六段自然输出没有提供给固定协议，评阅由实现者完成、非独立盲评，不报通用准确率。新样本保持评测用途，不加入优化器。
