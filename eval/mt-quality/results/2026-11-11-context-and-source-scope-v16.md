本轮修复已有模型的请求上下文和解码器，没有训练、量化、上传或切换权重。局部范围的新保守规则仍默认关闭。模型是 `PageLingo-Translate-1.8B-v0.2.2-Q5_K_M.gguf`，1,298,755,616 B，SHA-256 `8f8734198ad9332db97101de3ae7216daa3b59218522c4e0beebdfb4999924cc`。基模仍为 `tencent/Hy-MT2-1.8B`。

[机器记录](2026-11-11-context-and-source-scope-v16.json)保存实际请求摘要、输出、逐组统计、资源数据、源码版本和局限。[合同](../SOURCE_CONCEPT_GUARD_V16.md)说明生产修复与实验策略的边界。语义结论来自助手定向检查，未经独立人工盲审。

## 生产请求的成对测试

生成前按原网页结构选择八个来源：Django 四条事务目录链接、PostgreSQL 一个编号标题和一个带 BEGIN/COMMIT 的段落、Wikipedia 金融交易的标题和定义段落。每个来源的两组原 HTML、固定槽、自然内容、定位器和 URL 相同；只对上下文目录作旧版/当前版覆盖。实际调用现有 PageTranslator 请求构造器，冻结完整消息、grammar、预算及摘要后再推理，无完整中文答案注入。

| Django 原标题 | 原上下文目录输出 | 补充数据库上下文及术语后 |
| --- | --- | --- |
| Django’s default transaction behavior | Django 默认的事务行为 | Django 的默认事务行为 |
| Tying transactions to HTTP requests | 将交易与 HTTP 请求关联 | 将事务与 HTTP 请求关联 |
| Controlling transactions explicitly | 明确控制交易 | 明确控制事务 |
| Deactivating transaction management | 关闭交易管理 | 关闭事务管理 |

这里“明确/显式”是措辞选择，不因此判成错义。SQL 术语由请求传入，用户自定义术语仍优先；只对受限数据库文档路径加领域，不在译文生成后替换“交易”。金融标题两组都是“金融交易”，定义段落两组原始输出完全一致，没有 SQL 上下文或术语泄漏。

PostgreSQL 原标题的编号分隔符是 U+00A0。原模型输出分别改成 U+0020、U+3000，因而补充了解码期的源字面分隔符还原，要求编号不变。最终 Firefox 中两组均为 `3.4.\u00a0事务`，原锚点仍在。改号、丢号及只输出编号由单元测试验证整段拒绝。

生成后只有 `fixed-text.ts` 的上述解码修复改变，生成时的 71 项源码和原 runtime 均另行冻结。两组生产回放都使用最终解码器，只有领域目录覆盖不同；回放再次严格核对实际消息、grammar、预算和源内容与冻结请求一致，才喂入原始生成结果。没有重新生成来改善成绩。

16 次实际生产回放使用 PageTranslator + inferMtHtml，全部验证原树/节点/属性、祖先结构、代码、href/onclick 身份、自定义非导航监听器、精确 HTML 还原和原 Text 节点身份。PostgreSQL 段落仍有“通过用……围绕……来设置事务”这类生硬表达；金融定义仍残留英文 `A` 及“通信”的生硬措辞。本轮证明了定向术语修复，不构成整体翻译质量或完整网页覆盖率的通用分数。

## CPU 和系统实测

Debian 13.6、Linux 6.18.57、AMD EPYC 9V74，三个可见逻辑 CPU、cgroup 配额两核、内存上限 8 GiB，无 GPU。磁盘可用空间曾耗尽，首次复杂页 preview 在创建目录时失败，当时新译文推理尚未开始。核验旧证据 ZIP 的字节 SHA/CRC 后回收重复解包副本，再仅恢复失败阶段；模型、训练项目和原始记录保留。
